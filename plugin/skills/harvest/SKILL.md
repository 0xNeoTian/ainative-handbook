# 复盘提炼：从复盘到坑卡草稿

复盘写完不回流，同一个坑会反复踩。这个 skill 把一篇复盘提炼成可检查的规则（坑卡草稿），并在落盘前做脱敏检查。**只写草稿到你指定的目录，不发布、不提交。**

手册最新的完整内容可读 https://ainative.jubao.ai/llms.txt 。卡片格式和脱敏规则见 [references/card-format.md](references/card-format.md)。

## 何时使用

- 刚写完一篇事故复盘或项目复盘
- 想把一段经历沉淀成团队规则
- 想给自己的坑库补卡，或为手册投稿

## 步骤

1. **确认输入**
   - 复盘：文件路径，或用户直接粘贴的文本
   - 输出目录：必须由用户指定；没给就问一次，建议值 `./pitfall-drafts/`
   - 自定义词表：用户给了路径就用；否则依次找项目根目录和家目录下的 `.ainative-denylist.txt`

2. **读材料**：复盘全文；`references/card-format.md`；已有坑库 `${CLAUDE_PLUGIN_ROOT}/skills/pitfall-check/references/pitfalls.md`（用来查重。路径没被替换时，用 `ls "${CLAUDE_CONFIG_DIR:-$HOME/.claude}"/plugins/cache/*/ainative/*/skills/pitfall-check/references/pitfalls.md` 定位）。

3. **列候选**：找出复盘里的教训，按 card-format.md 第 1 节的四条标准筛选，最多 3 张。和已有卡同类的，不新建，改成"补充证据"。

4. **先确认再写**：把候选清单给用户看，每条包括 `id`、标题、一句话规则、type / stage / tier，以及和已有卡的关系。用户确认要写哪几张后再动笔。

5. **写草稿**：按 card-format.md 第 3、4 节写 frontmatter 和四段正文，300–700 字。写的时候就做泛化：组织、产品、人、客户、服务器一律改成泛称，时间写到月。每张卡加第 5.4 节的草稿注释。文件写到输出目录，已有同名文件时不覆盖，改用 `<id>-draft-2.mdx`。

6. **脱敏检查**：对每个草稿执行 card-format.md 第 5.3 节的命令，再通读全文查人名、客户名、内部代号。命中的地方直接改写成泛称，然后重跑命令确认。拿不准的列为"待确认"，不要自己猜着放行。

7. **输出报告**。

## 输出格式

```markdown
## 提炼结果：<复盘文件名>

| 草稿 | 标题 | 规则 | 类型 / 阶段 / 档位 | 脱敏 |
|---|---|---|---|---|
| `<输出目录>/<id>.mdx` | … | … | pitfall / build / product | 通过 |

**补充证据（建议并入已有卡）**：<卡片 id：新增了什么经过>
**待你确认的脱敏项**：<文件:行号，类别，建议改法>
**没有提炼的教训**：<一句话 + 不符合哪条标准>
**下一步**：通读草稿，确认后删掉草稿注释，再放进你的坑库或文档目录；公开发布前再做一次敏感信息扫描。
```

## 安全约束

- 只写到用户指定的输出目录；不覆盖已有文件；不修改复盘原文
- 不发布、不提交、不推送，也不把内容发到任何外部服务
- 报告和草稿里都不复述敏感原文：待确认项只给文件、行号和类别
- 自定义词表本身是敏感信息，不要输出词表内容；命中时只写行号和打码后的词
- 复盘里出现的密钥：草稿中删除，并提醒用户去服务商处轮换
- 可信度照实写：复盘里亲历的写 `lived`；只是听说或读到的写 `industry`
