## 首发长串推（发布日）

1/ 我带着几位协作者，主要靠 Claude Code 运营两个组织、十几个代码仓库、几十个 agent。半年写了 70 多篇复盘。今天把它们整理成了一本公开的手册：AI Native 手册。每条规则，都标明出处。🧵

2/ 写它的起因：本地数据库被清空过一次，之后我加了三层防护。几个月后一查，三层全没了：备份脚本两个多月前被一次上游合并冲掉；权限规则和 hook 的挂载，被配置切换工具的一次覆盖一起带走。恢复手册里写过检查命令，可它只是一段文字。

3/ 所以这本手册里，能变成命令的写成命令，能变成模板的写成模板，能变成 hook 和 skill 的做成了插件。三档路径：小工具 → 产品（AI-native 六阶段）→ 组织（ops 仓、组织级 agent、记忆分层）。首选 Claude Code，方法也适用于 Codex 等工具。

4/ 每一页都标了可信度：✅ 亲历 / 🧪 试用中 / 📚 业界做法；每张坑卡都标了依据的时间。上线前我把 94 条说法逐条对回原始复盘和记录，改掉了 59 处“记得不准”的细节。

5/ 手册本身也是一个 Claude Code 插件：给你的环境体检、按档位配置工具链、用 25 张坑卡审查你的改动。

## 坑卡短推（每周 3–4 条，按此顺序）

### 01 · 防护规则会悄悄失效

本地库被清空后，我加了三层防护：脚本先备份、权限要确认、hook 自动备份。半年后排查环境才发现三层全没了，原因只有两个：备份脚本被一次上游合并冲掉；权限规则和 hook 的挂载，被切换工具的一次整份覆盖一起带走。护栏失效不会报错，所以得定期体检。

依据：2026-05 复盘、2026-10 工作记录　链接：https://ainative.jubao.ai/docs/pitfalls/guardrails-decay

### 02 · 自己审自己等于没审（原则卡）

让写代码的模型自己审自己，它多半会认同自己。有一次它审完就说能合并，我坚持再审一遍，第二遍就在文档里翻出约 85 处改名残留。另一次换一个不同家族的模型做终审，抓出 2 个它漏掉的高优先级安全问题。这些类型检查一处都看不到。现在重大改动必须异构二审，我来拍板。

依据：2026-05 复盘与工作记录　链接：https://ainative.jubao.ai/docs/pitfalls/cross-model-review

### 03 · 插件不是越多越好

我一度装了 39 个插件、72 个 subagent，觉得越全越好。后来把最近 30 天的会话记录翻出来统计（默认只留这么久），被调用过的 skill 只有二十个左右，涉及的插件寥寥几个。剩下的每个会话都在吃上下文，还可能在后台抢触发。按数据砍到 16 个插件、19 个 subagent。

依据：2026-10 工作记录　链接：https://ainative.jubao.ai/docs/pitfalls/plugin-bloat

### 04 · 切换工具会整份覆盖设置

我用一个模型供应商切换工具切回官方模型，打开 Claude Code 发现插件全关了。一查才知道 ~/.claude/settings.json 被整份重写，16 条 deny、25 条 ask 和一个备份 hook 也一起没了，护栏静悄悄失效。现在每次切换完，先核对权限、hook、插件这三项还在不在。

依据：2026-10 工作记录　链接：https://ainative.jubao.ai/docs/pitfalls/config-overwrite

### 05 · 亲眼看到才算完成

加一个“全屏”按钮，状态切换的单测全绿，agent 说做完了。我自己点了一下：界面纹丝不动。组件库默认样式的优先级更高，把新 class 盖掉了。为这一个按钮，多返工了一轮。现在 UI 改动没亲眼看到结果，就不算完成。

依据：2026-05 复盘　链接：https://ainative.jubao.ai/docs/pitfalls/see-it-to-ship

### 06 · 不让 agent 动 git 历史

一个子 agent 觉得状态“不对”，自作主张跑了 git reset，丢了一个 commit；后面的 rebase 又让 5 个提交的哈希全变了。现在 reset、rebase、force push 一律不让 agent 自己动；真要动，我自己来，先把改动存好，再留一个 rescue 分支。

依据：2026-05 复盘　链接：https://ainative.jubao.ai/docs/pitfalls/git-history-no-surgery

### 07 · 同一个组织的记忆不要按目录分裂

我一直以为 Claude 记得我踩过的坑。直到发现：在组织的父目录启动，它有 200 多条记忆；进到子仓库启动，只剩 7 条。两边互相看不到，父目录里记下的坑，子仓库会话一条也不知道。自动记忆是按启动位置分家的，同一个组织得统一一个记忆目录。

依据：2026-10 工作记录　链接：https://ainative.jubao.ai/docs/pitfalls/split-memory

### 08 · 分段审过了，还要整分支终审

一个功能拆成 8 个任务，每个任务都单独过了异构模型审查。合并前我还是对整个分支做了一次终审，又抓出 5 个跨文件交互的深层 bug。每一段都对，合在一起不一定对。现在合并前必须整分支再审一遍。

依据：2026-08 复盘　链接：https://ainative.jubao.ai/docs/pitfalls/whole-branch-review

### 09 · 本地数据库也要按生产对待

一条破坏性的数据库命令，清空了我本地库里几个演示工作区，连同里面的 agent 配置，没有任何备份。那些都是一点点手工攒的，别处没有第二份，最后靠翻会话记录花了一天半才重建。“本地”不等于“可以重来”：库里有别处没有的数据，它就是生产。现在任何破坏性操作前先 dump，备份失败就不执行。

依据：2026-05 复盘　链接：https://ainative.jubao.ai/docs/pitfalls/local-db-is-prod

### 10 · “之前是这样的”先查 git

我跟 agent 说：“以前聊天和预览是并排显示的。”它当成“恢复旧功能”，直接做了一个 PR。我说不对，它又开一个 PR 撤回，再往后才去查 git：从来没并排过，那是我脑子里的新设计。白做了 6 个 commit，先查证只要半分钟。现在谁说“之前是这样的”，包括我自己，都先查 git。

依据：2026-05 复盘　链接：https://ainative.jubao.ai/docs/pitfalls/memory-vs-git

### 11 · 本机代理会让 DNS 检查失真

刚改完 DNS，我照例 dig 一下，返回的全是 198.18 开头的地址，第一反应是记录还没生效，差点就这么报告了。换 DoH 一查，记录早就生效了：本机代理开着 fake-ip 模式，53 端口的查询全被它截了，连指定公共 DNS 都没用。现在验证 DNS 一律用 DoH。

依据：2026-05 工作记录　链接：https://ainative.jubao.ai/docs/pitfalls/dns-fake-ip

### 12 · 发版靠清单，不靠感觉

有一次发版，安装包传了，云端也部署了，唯独漏传了 CDN 主源。用户的自动更新卡在旧版本将近一天，我还以为发完了。发版漏一步不会报错，只会安静地少一块。现在发版按清单逐项打勾，每项都有验证命令，清单写进 skill。

依据：2026-08 工作记录　链接：https://ainative.jubao.ai/docs/pitfalls/release-checklist

### 13 · 网络报错先查远端

一次发版，合并 PR 时 GitHub 返回 503，响应没回来。我没核实就接着打了 tag，其实合并已经成功，tag 却打在了合并前的提交上，只好删 tag 重打、删 release 重跑。超时只代表“不知道成没成”。现在网络报错后，先用 git ls-remote 或 gh api 查远端，再决定重试还是继续。

依据：2026-08 工作记录　链接：https://ainative.jubao.ai/docs/pitfalls/verify-remote-first

### 14 · 计划和执行分开会话

一次 55 个冲突的上游大合并，我在同一个会话里先写计划再执行。计划前后审了 6 轮，光写计划就把上下文烧光了；执行时会话差点跑不完，计划里一个关键决策还是错的。现在规模一大就拆：计划写成文件、审完、合并，关掉会话；再开一个新会话，只读计划去执行。

依据：2026-05 复盘　链接：https://ainative.jubao.ai/docs/pitfalls/split-plan-exec

### 15 · 模板复制后会各自漂移

第二个组织起步时，我把第一个组织的 ops 规则文件整份复制了过去。半年后回头看：6 处引用指向根本不存在的文件，“下次 review 日期”两边一字不差，而且已经过期半年。复制完的那一刻，两份就开始各走各路。共用的规则做成能继承的模板，别复制。

依据：2026-10 工作记录　链接：https://ainative.jubao.ai/docs/pitfalls/template-copy-drift

### 16 · 跟代码绑定的文档跟代码放一起

我有一份数据库恢复手册放在 ops 仓，白纸黑字写着“reset 前 Makefile 会自动备份”，开头还写了检查命令。结果代码仓那边，两个多月前的一次上游合并早把这段备份逻辑冲掉了。手册不知道，检查命令也没有任何机制去跑。跟代码绑定的文档就该跟代码放一起，检查写进 CI。

依据：2026-10 工作记录　链接：https://ainative.jubao.ai/docs/pitfalls/code-coupled-docs

### 17 · 跨仓链接用完整地址

我在代码仓的 10 个文档里写了二十多处 ../ 开头的相对链接，指向隔壁的 ops 仓。它们只在两个仓并排放的本机上点得开：换到 worktree，路径往上数就落空；GitHub 网页只解析本仓库内的相对路径；云端 agent 压根没有 ops 仓。跨仓引用，就写完整 URL。

依据：2026-05 复盘、2026-10 工作记录　链接：https://ainative.jubao.ai/docs/pitfalls/absolute-cross-repo-links

### 18 · 一个域名只挂一个平台

我有个子域名，DNS 早就指向新平台的静态站，旧托管平台上却还留着一个早期项目的绑定，从没生效过。清理时我想干脆把整个主域名从旧平台移除，动手前查了一圈依赖，才发现同一主域下另一个子域名正由旧平台提供服务，一删就下线。最后只删了残留项目。一个域名只挂一个平台，删之前先查全家。

依据：2026-10 工作记录　链接：https://ainative.jubao.ai/docs/pitfalls/one-domain-one-platform

### 19 · 性能修复先问六个问题（原则卡）

有一次 agent 修完一个调度上的性能问题，报告说快了很多。我追问：不会是为了速度砍掉了别的东西吧？它按六个角度逐条举证。从那以后，性能修复上线前我固定问六个问题：是修 bug 还是砍保护？有没有竞态？类似的地方改全了吗？上线后能看到生效吗？边界情况试了吗？失败了怎么发现？答不出就不上线。

依据：2026-05 复盘　链接：https://ainative.jubao.ai/docs/pitfalls/perf-fix-six-questions

### 20 · 同一时间只让一套流程自动接管（原则卡）

2026-10 准备从 superpowers 切到 Matt Pocock skills 时，两套插件同时装着。按官方文档，superpowers 在会话开始注入流程，Matt 有 11 个 skill 可以被模型自动调用，两者会争同一类请求，比如一句“帮我 debug”。所以切换当天我先停用 superpowers，再开始试 Matt。规矩：只留一套自动触发。

依据：2026-10 切换流程引擎时的分析　链接：https://ainative.jubao.ai/docs/pitfalls/one-process-engine

### 21 · 子 agent 别为省钱降级（原则卡）

我在 2026 年 5 月定了一条规矩：子 agent 一律用最强模型。项目里跨字段的约束多，子 agent 只拿到一段上下文，没写明的约束要靠它自己从代码里推；降级单次看不出问题，累积起来审查兜不住。子 agent 的成本不是瓶颈，质量才是。纯机械的活儿例外。

依据：2026-05 定的规矩　链接：https://ainative.jubao.ai/docs/pitfalls/subagent-strongest-model

### 22 · 实质改动先留文档再动手（原则卡）

好几次 agent 交回来的结果是对的，可它是直接上手改的代码，没留 spec，也没留 plan。当下看不出问题，等到要审计、要交接、要找人 review 时才发现：除了一个 diff，什么都没有。现在的硬规则：实质改动先写 spec 和 plan，再按 TDD 实现。

依据：2026-06 工作记录　链接：https://ainative.jubao.ai/docs/pitfalls/process-before-code

### 23 · CI 绿了不等于能发版

一次发版当天，CI 有一项检查从上一个合并开始变红，我们判断是环境差异，红着发了版。当天就收到三个问题报告，第二天的版本又让老用户一升级就崩溃，这些都不是那项红灯能拦住的。可“红着也能发”的先例一开，CI 就没人当真了。现在发版前，我在本地把单测、全量测试、类型检查、lint 全跑一遍。

依据：2026-08 复盘与工作记录　链接：https://ainative.jubao.ai/docs/pitfalls/ci-green-not-ready

### 24 · 对外内容先读权威文档

有一次让 agent 写对外材料，它没读现有的方案，凭记忆写了两版，写得很顺，读着也像那么回事，可定位整个写偏了，关键论据也漏了。我看完直接打回，让它先读最新的方案再写。人和模型的记忆都是旧快照。现在写 README、方案、对外介绍之前，先读权威文档，每个数字都标出处。

依据：2026-05 复盘　链接：https://ainative.jubao.ai/docs/pitfalls/read-canonical-first

### 25 · 临时方案要写明撤销条件

为了绕开系统更新框架对未签名安装包的拒装，我在客户端自动更新里加了一套自己写的安装流程，当天就写明撤销条件：拿到开发者证书就撤。五个月过去，证书没办，绕路还在，期间它还埋了个更新的坑。好在条件写下来了，每次复盘都会被提起。没写条件的“临时”，才是真的会被忘掉。

依据：2026-05 复盘、2026-06 工作记录　链接：https://ainative.jubao.ai/docs/pitfalls/temp-fix-revert-trigger
