## 发生了什么

有一次上游合并收尾，主力模型自己审完，说可以合并了。我要求合并前再审一遍：原本想交给另一个模型家族，它那次因为工具故障没给出结论；可就是这“再看一遍”，同一个模型的第二遍在文档里翻出约 85 处改名后的残留（旧产品名和旧命令）。类型检查和测试全绿，一处也拦不住。

同一个月的另一次，一个功能做完，我让另一个模型家族做终审。它给出 9 条发现，其中 2 条是主力模型漏掉的高优先级安全问题。

## 为什么会这样

自审的模型和写代码的是同一套偏好。读到自己的实现时，它会顺着当初的思路去理解，“我这样写是因为……”读起来总是合理的。如果审查还在同一个会话里，上下文里的错误假设也会被原样继承。自审能挑出一些低级错误，但替代不了独立的批准。

换一个模型家族，训练数据和偏好都不一样，盲区未必重合。我手里只有几次成功的例子，证明不了“盲区一定不重合”；能说的是，异构审查多次带来了自审没给出的增量发现。“再审一遍”本身也有用：第一次自审说能合并，第二遍就翻出了几十处问题。但它替代不了异构审查，同一个模型看第二遍，用的还是同一套偏好。至于改名残留这类内容问题，工具链本来就不管：类型对、测试过，不代表文档写对了。

Anthropic 的 [The AI-native SDLC playbook](https://claude.com/resources/articles/the-ai-native-sdlc-playbook) 在发布阶段也设了同样的关卡：写代码的 agent 不能批准自己的改动。

## 怎么做

<Steps>
<Step>

**主力模型写完，换一个模型家族审**。我用 Codex CLI：

```bash
codex review --base main -c model_reasoning_effort=medium
```

推理强度 medium 就够，xhigh 可能卡很久。装了 gstack 也可以直接用 `/codex`。Kimi、Gemini 也行，关键是不共享上下文，也不共享同一套模型偏见。

</Step>
<Step>

**审查者只拿 diff 和 spec，不拿对话记录**。它要知道“要做什么”和“改了什么”，不需要知道主力模型当时是怎么想的。

</Step>
<Step>

**plan 阶段就可以审一次**。跨字段的不变量问题，在计划里就能抓到，比写完代码再返工便宜得多。

</Step>
<Step>

**人最后拍板**。审查意见按严重程度列出，改哪些、不改哪些由人决定，结论留在 PR 里。涉及对外内容的改动，再加一轮人工通读。

</Step>
<Step>

**用数据评估这个组合值不值**。这一步我还没有系统做过。如果要长期用，建议每次二审记几笔：抓到几个主力模型漏掉的真问题，提了几个误报，花了多少时间和钱；再加上线后才暴露、两边都没审出来的漏报。攒一段时间，再决定换不换模型、是不是每次都审。

</Step>
</Steps>
