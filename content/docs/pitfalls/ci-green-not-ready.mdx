## 发生了什么

一次发版当天，后端 CI 有一项检查从上一个合并开始变红。我们判断是 CI 和本地的环境差异，就红着发了版。

那个版本发出去当天就收到三个问题报告；第二天的下一个版本，老用户一升级就启动崩溃。那项红灯后来查明是假红：测试本身会扫描运行环境，跟这些问题都无关。复盘时发现两件事：“红着也能发”的先例一开，CI 的信号就不再有人当真；而那次崩溃，全绿的 CI 本来也测不到。

## 为什么会这样

两层原因。

第一，“环境问题”是一个标签，不是诊断。CI 和本地、生产之间的环境差异，恰恰是 CI 应该暴露的东西。一旦接受某个红灯是常态，红色就成了噪音，真正的失败也会混在里面被放过。

第二，CI 本来就只覆盖一部分。为了快，常见做法是按路径过滤、跳过慢测试和不稳定的测试、复用缓存。CI 全绿说明的是“这部分没坏”，不是“这个版本能发”。

## 怎么做

<Steps>
<Step>

**红灯不能常驻**：要么限期修好，要么明确隔离，在 CI 配置里把它改成非必需，同时开 Issue 写清负责人和恢复条件（见[临时方案要写明撤销条件](/docs/pitfalls/temp-fix-revert-trigger)）。不接受“心里知道它是红的”。

</Step>
<Step>

**红了先看日志，不靠猜**：

```bash
gh pr checks                        # 当前分支 PR 的全部检查
gh run view <run-id> --log-failed   # 只看失败步骤的日志
```

</Step>
<Step>

**发版前本地跑全量验证四件套**：单测、全量测试（含集成或 e2e）、类型检查、lint。串成一条命令，任何一步失败就停（脚本名按项目改）：

```bash
bun test && bun run test:e2e && bunx tsc --noEmit && bun run lint
```

</Step>
<Step>

**关键检查在分支保护里设为 required**，红着就合不进去。

</Step>
</Steps>
