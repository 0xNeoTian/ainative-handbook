## 发生了什么

有同事反馈，客户端更新提示里的“立即重启”点了没反应。查下来是系统的更新框架拒装未签名的安装包。为了绕开它，我在客户端自动更新里加了一套自己写的安装流程。这是个临时绕路，当天就在仓库文档和记忆里写明了撤销条件：拿到开发者证书就撤，换回标准的更新路径。

五个月过去，证书还没办，绕路还在。期间它自己又埋了个坑：只有点“立即重启”才会安装，直接退出应用不装，错过提示的用户就一直停在旧版，后来专门修了一次。好在撤销条件写了下来，之后的复盘一再提到它，它没有被忘掉。没写条件的“临时”，才是真的会被忘掉。

## 为什么会这样

加和撤的成本严重不对称。赶时间的时候，`--no-verify` 跳过检查、写死一个兜底值，都是几秒钟的事；撤掉它却需要有人记得、有人负责，还得等到合适的时机。

临时方案通常缺三样东西：负责人、撤销条件、记录。“什么时候撤”只存在于加它的那个人脑子里，发版压力一过，再没有任何事件会让人想起它。

agent 让这件事更糟。新会话看不到“这是临时的”这段口头背景，只看到一段正常运行的代码，会把它当成既定设计，在上面接着搭。

## 怎么做

适用范围：`--no-verify` 提交、硬编码的兜底值、为赶时间加的绕路、临时关掉的检查。

<Steps>
<Step>

**在代码里标出来**，写明为什么加、什么条件下撤：

```ts
// TEMP(#123): 安装时绕过 X，为赶 v1.4 发版
// 撤销条件：上游修复 X 并发版后，删除本段
```

</Step>
<Step>

**PR 描述里单列一节**：

```markdown
## 临时方案
- 做了什么：
- 为什么：
- 撤销条件：（具体到版本、日期或事件）
- 跟踪 Issue：#123
```

</Step>
<Step>

**记入待撤清单**，用一个固定的 Issue 标签：

```bash
gh label create temp-fix --description "待撤销的临时方案"   # 只需建一次
gh issue create --title "撤销：安装流程临时绕路" --label temp-fix --body "撤销条件：……"
gh issue list --label temp-fix   # 待撤清单
git grep -n "TEMP("              # 代码里还剩哪些
```

</Step>
<Step>

**定期过一遍**：放进每周复盘，或者用 `/schedule` 建一个定时运行的 agent，检查撤销条件是否已经满足。<Evidence kind="trial" />

</Step>
</Steps>
